# CS-360
     This app was built to make basic stock tracking fast and reliable for a small warehouse team. The main goal was to let users add an item quickly, see quantities at a glance, and keep data safe on the device without a network. The app addresses common needs such as simple entry, clear status, and persistence across sessions. 
     The interface focuses on a few screens that support those needs. A login and registration screen handles access. A dashboard shows items in a two-column grid with an item name, quantity, and a color dot that indicates stock level. A small dialog handles add and edit so updates take only a moment. An optional SMS screen requests permission if the user wants to receive low stock texts. I kept one primary action per screen and used clear labels and comfortable touch targets. This kept the path obvious and reduced confusion. 
     My coding approach was problem-first and user-driven. I wrote a short problem statement, sketched the flow, and then built the app in small end-to-end pieces that connected screen, behavior, and data so I could run the full path early. I kept names clear and added short comments to explain intent so the code was easy to follow. I plan on using this same approach in future projects. It helps keep the scope clear, supports successful iteration, and makes the code easier to maintain.
     For testing, I started by registering, logging in, adding items, editing items, deleting items, then closing and reopening the app to make sure that data persisted across sessions. I checked that the color thresholds matched the rules and that the toolbar action and floating button were visible and responsive. For the SMS screen, I denied the SMS permission to confirm the app still operated correctly without it, and then granted it to verify that a low stock save could send a text. 
     In terms of innovation, the main challenge in this project was balancing an offline-first design with a feature that uses a sensitive permission. I chose to keep SMS as an optional path and requested permission only when the user chose to enable so that the core task never depended on it. I also refined the layout so the floating action button sat above the grid and the app bar consistently showed its actions, which improved reliability across devices.
     The component that best shows my skills is the combination of the local data layer and the dashboard. SQLite persistence keeps the inventory stable across sessions, and the grid with three color indicators makes stock status easy to identify. Together, they create a simple path for routine updates and paint a clear picture of stock health for the user.
